# 운영 비밀정보 백업·복구 설계

## 목표

개발 노트북을 분실하거나 사용할 수 없게 되더라도 새 장비에서 Researchi Admin의 개발과 운영 유지보수를 재개할 수 있어야 한다. 소스 코드, 운영 설정, 인증 정보, 데이터베이스 백업을 한 서비스나 한 장비에만 의존하지 않으면서 실제 비밀값은 GitHub에 평문으로 남기지 않는다.

복구 목표는 다음과 같다.

- 새 장비에서 소스 코드와 빌드 환경을 복원한다.
- 로컬 및 운영 설정 파일을 원래 구조로 재생성한다.
- AWS, GitHub, Bitwarden 계정 접근 권한을 복구한다.
- 필요한 경우 데이터베이스와 운영 파일을 별도 백업에서 복원한다.
- 분실 장비가 제3자에게 노출됐을 가능성에 대비해 기존 자격 증명을 교체한다.

## 설계 원칙

1. GitHub private 저장소는 소스 코드와 암호화된 설정의 버전 관리에 사용한다.
2. 토큰, 비밀번호, 개인키 및 개인정보가 포함된 데이터는 Git에 평문으로 저장하지 않는다.
3. SOPS와 age로 설정값을 암호화하고 암호화 결과만 커밋한다.
4. age 개인 복구키는 Bitwarden에 보관하며 GitHub와 노트북에만 의존하지 않는다.
5. Bitwarden 및 GitHub의 복구 코드는 종이 복구 키트로 별도 보관한다.
6. DB 덤프와 대용량 운영 파일은 Git이 아닌 별도 클라우드 저장소에 암호화해 보관한다.
7. 백업 생성만으로 완료하지 않고 정기적으로 새 환경에서 복구 가능 여부를 검증한다.

## 저장 위치별 책임

### GitHub private 저장소

GitHub에는 다음 항목을 저장한다.

- 애플리케이션 소스 코드와 빌드 파일
- 공개 가능한 설정 예시
- SOPS로 암호화된 로컬 및 운영 설정
- `.sops.yaml`의 age 공개 recipient
- 배포, 백업 및 복구 절차 문서
- 외부 백업에 포함돼야 할 항목을 기록한 복구 명세

다음 항목은 저장하지 않는다.

- 평문 `application-local.yml`, `application-prod.yml`, `.env`
- 평문 API 토큰, DB 비밀번호, SMTP 비밀번호
- 평문 `*.pem`, `*.key`, `*.p12`, `*.jks`
- 평문 또는 단순 압축된 DB 덤프
- age 개인 identity
- Bitwarden 마스터 비밀번호와 계정 복구 코드

권장 파일 구조는 다음과 같다.

```text
src/main/resources/application-example.yml
secrets/application-local.sops.yml
secrets/application-prod.sops.yml
.sops.yaml
docs/RECOVERY.md
docs/BACKUP-INVENTORY.md
```

복호화된 파일은 기존 위치를 유지한다.

```text
src/main/resources/application-local.yml
/etc/researchi-admin/application-prod.yml
```

복호화된 파일은 `.gitignore`로 계속 제외한다. 암호화 파일에는 SOPS 메타데이터가 포함되므로 SOPS를 통하지 않은 수동 편집을 금지한다.

### Bitwarden

Bitwarden에는 다음 항목을 보관한다.

- age 개인 identity
- GitHub 계정 정보
- AWS 계정 정보
- 운영 서버 접속 정보와 서버별 메모
- DB, SMTP, SMS 등 외부 서비스 계정의 식별 정보
- 외부 암호화 백업의 위치와 복호화 방법

설정 파일에 들어가는 실제 비밀값의 기준본은 SOPS 암호화 파일로 관리한다. Bitwarden은 age 키와 계정 복구 정보의 안전한 보관소로 사용하며, 같은 값을 두 위치에서 수동으로 각각 관리해 불일치가 생기지 않게 한다.

Bitwarden 계정에는 강한 마스터 암호와 2단계 인증을 적용한다. 마스터 암호 자체는 Bitwarden 안에 저장하지 않는다.

### 종이 복구 키트

봉인한 종이 복구 키트에는 다음 항목을 기록한다.

- Bitwarden 마스터 암호 또는 이를 확실히 복원할 수 있는 복구 정보
- Bitwarden 2단계 인증 복구 코드
- GitHub 2단계 인증 복구 코드
- 주 이메일 계정의 복구 절차
- 외부 암호화 백업의 복호화 암호
- 문서 작성일과 마지막 복구 테스트 일자

종이 복구 키트는 노트북과 같은 가방이나 같은 책상에 두지 않고 별도의 잠금 장소에 보관한다. 사진을 촬영해 휴대폰 갤러리나 일반 클라우드 사진함에 저장하지 않는다.

### 별도 암호화 백업

GitHub와 Bitwarden을 동시에 사용할 수 없는 상황에 대비해 별도 클라우드 저장소 또는 오프라인 저장장치에 암호화 백업 한 세트를 유지한다.

백업 세트에는 다음 항목을 포함한다.

- 전체 이력을 포함한 Git 저장소 bundle
- SOPS 암호화 설정 파일과 `.sops.yaml` 사본
- Bitwarden의 비밀번호로 보호된 암호화 내보내기
- 필요한 운영 DB 덤프
- 사용자 업로드 등 DB 외부에 존재하는 필수 운영 파일
- Custom SSH 키와 직접 발급한 인증서가 있는 경우 그 암호화본
- 저장소 복구에 필요한 문서와 파일 목록
- 각 파일의 SHA-256 체크섬

외부 백업 파일은 강한 별도 암호로 암호화한다. 복호화 암호는 같은 클라우드 폴더에 저장하지 않고 종이 복구 키트에 보관한다.

DB 백업에는 신청자 개인정보가 포함될 수 있으므로 GitHub 저장소에 커밋하지 않는다. 단순 ZIP이나 파일명 변경은 암호화로 간주하지 않는다.

## SOPS와 age 키 구조

age 키 쌍은 다음 역할로 구분한다.

- 공개 recipient: `.sops.yaml`에 기록하고 GitHub에 커밋해도 된다.
- 개인 identity: 파일 복호화 권한이 있으므로 GitHub에 커밋하지 않고 Bitwarden에 보관한다.

로컬 장비에는 작업 중에만 age 개인 identity를 사용자 전용 설정 경로에 복원한다. 프로젝트 폴더 안에는 두지 않는다. 새 설정을 만들거나 기존 설정을 변경할 때는 SOPS를 통해 암호화 파일을 갱신하고 암호화된 변경만 Git에 커밋한다.

키를 교체할 때는 새 age recipient를 추가하고 기존 SOPS 파일의 데이터 키를 새 recipient로 재암호화한다. 새 키로 복호화되는 것을 확인한 후에만 이전 개인 identity를 폐기한다.

## SSH 키 처리

### Lightsail 기본 키

`LightsailDefaultKey-<region>.pem`은 GitHub에 저장하지 않는다. Lightsail 기본 키는 AWS 계정에서 해당 리전의 개인키를 다시 다운로드할 수 있으므로, 저장소에는 재다운로드 경로와 대상 리전만 문서화한다.

노트북 분실 시 기존 파일을 그대로 신뢰하지 않고 AWS 계정에서 다시 내려받는다. 분실 장비가 잠금 해제될 가능성이 있으면 서버의 `authorized_keys`를 점검하고 필요에 따라 새 키를 추가한 뒤 기존 키를 제거한다.

### Custom SSH 키와 직접 발급한 인증서

AWS가 개인키를 다시 제공하지 않는 Custom SSH 키와 직접 발급한 인증서는 외부 암호화 백업에 포함한다. Git으로 버전 관리할 필요가 있을 때만 age 또는 SOPS binary 모드로 암호화한 파일을 저장하며, 평문 원본은 계속 `.gitignore`로 제외한다.

장기적으로는 한 개인키를 여러 서버에서 공유하지 않고 장비 또는 관리자별 키를 등록한다. 분실 장비의 공개키만 서버에서 제거할 수 있도록 키 이름과 fingerprint를 복구 명세에 기록한다.

## 백업 주기와 보존

- SOPS 설정: 비밀값 또는 설정이 변경될 때마다 즉시 암호화 파일을 갱신하고 커밋한다.
- Bitwarden 암호화 내보내기: 월 1회 및 주요 계정 정보 변경 직후 갱신한다.
- 운영 DB: 매일 암호화 백업을 생성한다.
- 운영 파일: 매일 증분 또는 변경 시점 백업을 수행한다.
- 종이 복구 키트: 계정, MFA 또는 백업 암호 변경 직후 갱신한다.

DB 백업은 최근 일일본 14개, 주간본 8개, 월간본 12개를 보존한다. 백업 저장 용량이 부족해도 가장 최근 정상 복구가 확인된 월간본 한 개는 삭제하지 않는다.

## 노트북 분실 시 복구 절차

1. 종이 복구 키트로 주 이메일, Bitwarden, GitHub 및 AWS 계정 접근을 회복한다.
2. 분실 장비의 GitHub 세션, AWS 세션, 이메일 세션과 Bitwarden 세션을 해제한다.
3. GitHub 토큰, AWS 액세스 키, DB 비밀번호, SMTP/SMS 키 등 분실 장비에 존재했던 자격 증명을 교체한다.
4. 새 장비에 보안 업데이트와 전체 디스크 암호화를 적용한다.
5. GitHub private 저장소를 복제한다. GitHub를 사용할 수 없으면 외부 백업의 Git bundle에서 저장소를 복원한다.
6. SOPS와 age를 설치하고 Bitwarden에서 age 개인 identity를 사용자 전용 경로에 복원한다.
7. `application-local.sops.yml`과 `application-prod.sops.yml`을 복호화해 지정된 위치에 배치한다.
8. Lightsail 기본 키는 AWS 콘솔에서 다시 다운로드한다.
9. 필요한 DB와 운영 파일을 외부 암호화 백업에서 복원한다.
10. 애플리케이션 빌드와 테스트를 실행한다.
11. simulation 모드로 기동해 DB 조회, 공개 신청 폼, 메일 및 SMS 설정을 점검한다.
12. 모든 복구 항목을 확인한 뒤에만 scheduler와 실발송을 다시 활성화한다.

분실 장비를 되찾더라도 자격 증명 교체를 취소하지 않는다. 이미 폐기한 토큰과 키는 다시 사용하지 않는다.

## 복구 검증

분기마다 한 번 실제 운영 환경과 분리된 임시 폴더 또는 테스트 장비에서 복구 훈련을 수행한다.

검증 항목은 다음과 같다.

- GitHub 저장소에 평문 비밀파일이 추적되지 않는다.
- Bitwarden에서 age 개인 identity를 회수할 수 있다.
- SOPS 암호화 파일이 오류 없이 복호화된다.
- 복호화된 설정의 필수 항목이 `application-example.yml`과 일치한다.
- 외부 백업의 체크섬이 기록값과 일치한다.
- DB 덤프를 격리된 테스트 DB에 복원할 수 있다.
- Lightsail 기본 키 재다운로드 경로를 확인할 수 있다.
- 애플리케이션이 simulation 모드에서 빌드 및 기동된다.

검증 결과에는 실행일, 수행자, 성공 여부, 실패 원인과 조치 내용을 기록한다. 복호화된 파일과 테스트 DB는 검증 종료 후 안전하게 폐기한다.

## 실패 상황별 대응

- GitHub에 접근할 수 없음: 외부 암호화 백업의 Git bundle, SOPS 파일, 복구 문서와 Bitwarden 내보내기를 사용한다.
- Bitwarden에 접근할 수 없음: 종이 복구 키트와 외부 백업의 암호화된 Bitwarden 내보내기를 사용한다.
- age 개인 identity 손실: Bitwarden 또는 암호화된 Bitwarden 내보내기에서 복원한다.
- GitHub와 Bitwarden 모두 접근 불가: 종이 복구 키트로 계정 복구를 먼저 수행한다.
- SOPS 파일 손상: Git 이전 버전 또는 외부 백업에서 마지막 정상본을 복원한다.
- DB 최신 백업 손상: 체크섬이 정상인 이전 일일본, 주간본, 월간본 순서로 복원한다.
- 비밀값 평문 커밋 발견: 파일 삭제만 하지 않고 해당 자격 증명을 즉시 교체한 뒤 Git 이력 정리 필요성을 별도로 판단한다.

## 구현 범위

후속 구현에서는 다음 작업만 수행한다.

1. private GitHub 원격 저장소 연결 상태를 확인한다.
2. SOPS와 age 도구 및 키 쌍을 준비한다.
3. `.sops.yaml`과 암호화 설정 파일 구조를 추가한다.
4. `.gitignore`를 보강하고 평문 비밀파일 추적 여부를 검사한다.
5. `docs/RECOVERY.md`와 `docs/BACKUP-INVENTORY.md`를 작성한다.
6. 암호화, 복호화 및 평문 추적 방지 검증 명령을 제공한다.
7. 별도 암호화 백업 생성 절차와 정기 복구 점검표를 작성한다.

실제 운영 비밀값, age 개인 identity, SSH 개인키 및 DB 덤프는 구현 커밋이나 작업 로그에 출력하지 않는다. GitHub 저장소 생성, Bitwarden 계정 생성, 외부 클라우드 업로드처럼 계정 소유자의 승인이 필요한 작업은 각 단계에서 별도로 진행한다.
